Lesson 1 · How Elicit Works

The Shape of Elicit

You built this. This lesson is not going to teach you a library — it's going to give you the map you'd draw for someone else, so you stop holding the whole app in working memory every time you open src/server.ts. One win today: you'll be able to say, in order, what happens between opening Elicit and closing a sitting, and name the file behind each step.

One sitting, start to finish

A Sitting is the human-facing word; session is what the code calls it. Here is what happens, in order, the first time you open the app and answer one question:

you open the app → Elicitor → you answer → Harvester → Vault → Clerk → Wiki ↻
  1. Elicitor picks a question. startSession in src/elicitor/elicitor.ts opens the sitting; userTurn handles each answer you type. The question itself came from one of seven Question Sources (bank draw, composed follow-up, gap-fill, instrument step, randomizer draw, still-true revisit, verification) — that selection logic is its own lesson, coming later.
  2. You answer; the Harvester proposes cuts. propose and decide in src/harvester/harvester.ts break your prose into candidate Snippets — verbatim substrings only. You approve, trim, discard, or restate each one. Nothing the model wrote can become a Snippet; see CONTEXT.md's Sole Authorship invariant.
  3. Approved Snippets land in the Vault. createVault in src/vault/vault.ts is the archive: plain markdown with frontmatter, its own git repo, committed under the elicit-clerk identity so your hand-edits and the app's writes are always distinguishable in git log.
  4. The Clerk works the Docket in the background. runDocket in src/clerk/docket.ts is the standing task list. It runs between and during sittings — never mid-turn, never blocking you. It has grown into a real pipeline of a dozen-plus jobs, but they fall into three families: composing new questions for the waiting queue (from old answers worth re-asking, from recorded holes in the archive), sweeping the archive for one kind of thing at a time (essays gone quiet, references that dangle, people you keep mentioning), and consolidating — the claim-writing and contradiction-detection that maintains the Wiki, always the last job of a run. Each job is wired as an optional dependency the server injects; absent means that job doesn't run this pass — so the function's own deps type is the truest map of what's live right now, and Lesson 2 unpacks the question-composing family in full.
  5. The Wiki updates, citing its evidence. Every Claim the Clerk writes into the Wiki cites the exact Snippet versions it rests on. No claim, no citation — see src/wiki/store.ts and src/wiki/lint.ts, which enforces this mechanically.
  6. The loop closes. Whatever the Docket minted waits in the Queue (src/queue/queue.ts) for your next sitting. Nothing the Clerk does ever contacts you directly — per CONTEXT.md's Docket entry, "the user contacts the agent by opening the app."
Notice the shape: the model never writes your words, and the background never reaches for you. Both are structural rules, enforced by code (harvester rejects reworded text; Docket tasks only ever wait), not by prompting the model to behave. Keep this pattern in mind — it recurs everywhere in this codebase.

Two agents, not one

"The agent" is actually two model roles, defined in src/llm.ts:

RoleRunsBinding constraintDefault model
elicitorin front of you, livelatency — you're waitingbonsai-27b @ llama.cpp
clerkbehind you, backgroundinstruction-following — accuracy matters more than speedqwen3.6:35b @ Ollama

Each role reads its own base URL and model ID from the environment (ELICIT_LLM_* for elicitor, ELICIT_CLERK_* for clerk) via roleConfig(). The split is a default, not a hard coupling — either role can point anywhere. What is a hard rule: if a role's endpoint dies, roleFailure() fails loudly and names the role. The other role's model is never tried as a silent substitute — an artifact stamped with a model that didn't write it would be a lie the Wiki can't afford (this is the same evidentiary seriousness as Sole Authorship, one layer down).

Every call also carries a wall-clock timeout (180s default) and a max-token cap (16384), both overridable per call. These aren't tuning knobs left over from testing — src/llm.ts's comments cite the actual incident (an 84-minute runaway generation) that each bound exists to convert into a named, diagnosable failure instead of a silent hang.

Nineteen subsystems, five jobs

src/ has nineteen top-level directories. Most of them are supporting cast for the five roles you just walked through — Elicitor, Harvester, Vault, Clerk, Wiki — plus a few standalone concerns (auth, speech-to-text, memory consolidation). The full map, with one line per directory, is in reference/subsystem-map.html. And whenever any lesson uses a capitalized project word that doesn't click — Bud, Sounding, Marginalia — the plain-English glossary defines every one in ordinary language, with pointers to the precise CONTEXT.md versions.
