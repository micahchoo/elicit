One Docket Run

You know the turn order and you know the Queue draw. This lesson answers the question those two left open: who stocks the Queue, and when? One win today: know what wakes the background Clerk, name the jobs of one run in order, and know which of them are even capable of touching a model.

Five words first

New vocabulary this lesson leans on — one line each, full versions in the glossary:

mint background work creating something durable — a question into the Queue, a claim into the Wiki.
Reading the Clerk's recorded interpretation of one Snippet — the raw material claims are proposed from.
op one of six edits the model may propose against the Wiki — a gate applies or refuses each.
consolidation folding old transcripts into one-line summaries, so history fits a fixed reading budget.
watermark a git marker of "the last state the Clerk looked at" — a commit, not a timestamp.

What wakes the Clerk

The honest answer surprised me when I read for it: there is no timer anywhere. No cron, no interval, no scheduled anything. The docket runs when something you did creates work — and only then:

This is a design position, not an accident: the app's own rule is that agent initiative ends at the app's edge — nothing reaches out to you, so nothing needs to run while you're away. The cost is real too, and worth knowing as the author: a long-idle server does zero background work until you harvest, import, or restart.

The run, job by job

One run walks a fixed order. Three families: capped composing trickles, model-blind sweeps, and the heavy tail that always goes last:

Three structural facts about this pipeline are worth holding onto, because they're what makes background work trustworthy:

  • No job can kill the run. Every job sits in its own try/catch; a failure logs a named *-failed event and the run continues. Even inside loops: one snippet's failed opener doesn't stop the next snippet's.
  • "Model-blind" is enforced by wiring, not discipline. The sweep thunks are simply never handed the model handle (complete) — a sweep cannot develop a model call, the same way agent prose cannot enter a Piece.
  • The docket never imports the newer layers. Wiki jobs, import extraction, ladder summaries all arrive as pre-wired thunks injected by the server — the older, smaller module never depends on the things built on top of it.

Honest edges

Reading your own system closely also means naming what's half-built. Three edges the research turned up, in increasing order of "worth a look":

  • Consolidation writes; nothing reads. Summaries are faithfully written to the vault every run, but the "cover" tiler that would feed them into a prompt has no production caller — your own registry documents this. The three-layer memory design (ADR-0002) is live on the write side only.
  • The embedding clash channel is shadowed to zero. The channel that would surface meaning-level contradictions currently returns no pairs at all — only the shared-phrase and shared-name channels feed the judge. The Q-65 ranking (cross-sitting above same-sitting) is computed but never actually orders the pool.
  • A possible real bug: the docket hands sessions to the consolidation picker newest-first, but the picker and the (unwired) tiler both document oldest-first expectations — so summary ranges are built backwards relative to what the read side will expect when it's wired. Nothing breaks today precisely because nothing reads; it will matter the day the tiler gets a caller.
