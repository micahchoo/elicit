# The Clerk (Third Slice) Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Wiki exists as running code. Harvested readings become Claims with mandatory Range, mandatory cites, and mechanically-assigned Status; contradiction candidates surface, mint exactly one re-measure question, and open a Contradiction only on confirmation — on structurally verified evidence, never on a model's self-report; a zero-LLM graph lint adds questions and annotations and can never remove a claim; referents get a three-tier identity registry that never merges by inference. Every agent-authored artifact carries a model stamp, readings included. Every threshold arrives in shadow. All of it is markdown under `vault/wiki/`.

**One production bug is in scope, because the slice cannot run without it fixed:** queue entries never reach `answered` (ticket 041). `markAnswered` is defined and called by nothing, so a drawn entry stays `asked` forever. Q-30 stages 3–5 key on an answered re-measure, so without the fix they are unreachable outside a test that stages the state by hand. T17 owns the fix, in the live turn path.

**What this slice does NOT build:** the six-verb wiki-editing surface (Q-33) and Propagation. See *The UI decision* below — it is deliberately deferred, and the reasoning is load-bearing, not a punt.

**Architecture:** One new namespace, `src/wiki/`, owns almost every Clerk-slice concern and is created wholesale by this slice, so the agents currently live in `src/` never collide with it. `src/wiki/` is pure logic plus one persistence module; the LLM-touching pieces live in `src/clerk/` next to their existing kin. The Clerk stays the single writer to the Wiki: nothing outside `src/wiki/ops.ts` writes a claim, and `ops.ts` is the one code boundary where Q-29's invariants are checked (the wiki-side mirror of the harvester's Q-1 substring check). The existing `Vault` keeps snippets, readings, buds, and transcripts; it learns three frontmatter fields on a reading and nothing else.

Three files outside those two namespaces change, each for a stated reason and each owned by exactly one task: `src/queue/queue.ts` and `src/elicitor/elicitor.ts` (T17 — the answered-turn bug, without which half of Q-30 cannot run), and `src/log/format.ts` (T12 — Q-23 makes the log the audit trail, and an unformatted event kind renders as machine noise).

**Tech stack:** unchanged — TypeScript (`exactOptionalPropertyTypes: true`, `noUncheckedIndexedAccess: true`), gray-matter, ulid, Hono, Vitest, `@mariozechner/pi-ai` → llama.cpp `bonsai-27b` at `http://192.168.0.229:8088/v1`. **Plus one embedding endpoint** — Ollama at `http://192.168.0.229:11434/v1/embeddings`, `qwen3-embedding`, the provisional default Q-17 locks. See *The resonance problem*.

## Two constraints that shape everything below

### The resonance problem (eval finding #8)

Q-30 stage 1 says candidates come "from both channels (lexical + embedding)". `docs/eval-2026-08-02-claude-adversarial.md` finding #8 measured what exists today: a planted contradiction restated in fresh words produced **zero** hits, because `resonate()` is a 3-consecutive-word exact-match index. `tests/resonance-paraphrase.test.ts` has since recorded that number as a standing fixture — 8 belief/restatement pairs, measured recall 0/8.

This plan treats the candidate pool as **channel-agnostic by construction and ships three channels**:

- **lexical** — `resonate()` over a second `LexicalIndex` built from claim bodies. `buildIndex` takes `Snippet[]`, so the adapter is named and explicit (T11); the existing snippet index is not reused for this, because it cannot return claim pairs.
- **referent** — two live Claims naming the same canonical referent (the Q-32 registry). This channel is *new here* and does not depend on shared vocabulary: two claims about "my manager" collide because they point at the same entity, however differently they are worded.
- **embedding** — cosine over `qwen3-embedding`, the provisional default Q-17 locks, against the endpoint Q-17 records as live. Threshold shadow-first (Q-35); the index is derived and rebuildable (Q-3); an unreachable endpoint skips the channel cleanly and logs, and never fails the run.

`ClashChannel` is an interface and all three are implementations, so a fourth is additive. The embedding channel is **T18** and it is in scope: the wayfinder edge from ticket 008 to ticket 007 was cut on 2026-08-02 with the reason that Q-17 already locks the provisional default, so 007 tunes a parameter rather than deciding the architecture. Recall is therefore measured against the existing fixture, not asserted as poor: T11 records the two non-semantic channels' recall over `PAIRS`, and T18 records the semantic channel's, in test names, whatever the numbers turn out to be.

### The model problem (eval findings #1, #3, #6)

The same eval found bonsai-27b's instruction-following collapses at 3+ conversation turns (harvest silently returned nothing on every real-length sitting), and that model-self-reported booleans degrade to `true` under mild adversarial pressure. Generating a validated op list is a *harder* task than harvest JSON, on the same model.

Ticket 034 has since landed the fix for the first half: `src/harvester/harvester.ts:205-284` sends **one user turn per `complete()` call**, and `tests/harvest-chunked.test.ts` holds that shape. Q-44 states the rule for the second half in the register's own words — *a model self-reporting a boolean is a suggestion, not a check*.

Structural response, applied in every LLM-touching task here:

1. **One item per call.** No task in this plan puts two readings, or two judgments, in one payload. The unit is one reading (T6) or one claim pair (T7). Payload composition is per-item and capped; ops accumulate across calls in T12. This is the shape ticket 034 measured, adopted rather than re-litigated.
2. **Hard prompt caps, asserted in code before the call.** `capPrompt()` throws rather than sending an over-budget prompt — it is an assertion, not a policy. The policy is `fitPayload()`, which truncates the optional parts in a declared order and reports failure when the mandatory core alone will not fit. **Nothing over budget ever throws its way to the head of the sweep twice** — see *The head-of-queue rule* below.
3. **A model boolean is never the last word.** Every model claim that opens or contests something is verified in code against text the model was given: `judgeOpposition`'s poles must be exact substrings of the supplied quotes, and `judgeConfirmation` must return a verbatim fragment of a snippet the re-measure actually harvested (Q-44, eval finding #6). Unverifiable → the safe outcome, which is always "no new tension".
4. **KEEP is the safe default.** A call that fails to parse leaves its reading unprocessed for the next run (Q-29), which is a no-op, never a bad write.
5. **Rejected ops are logged with reason and skipped** (Q-29) — and the rejection rate is itself the metric that tells us whether the model can do this job at all.
6. **Every LLM call ends with a user-role message** (ticket 023 — llama.cpp 400s with `Jinja: No user query found in messages`, and generates nothing when the list ends on an assistant turn), enforced by `assertUserTurn()` from `src/wiki/contract.ts`, not by prompt discipline. Every LLM-touching test asserts it via the fake.
7. **Every LLM-touching job is try/catch-isolated** (ticket 023 item 2) — one failed judgment must never cost the rest of a docket run.
8. **Composed questions pass the shipped guards.** Anything this slice puts in the Queue runs `isInterrogative` and `hasFirstPersonOutsideQuote` from `src/elicitor/guards.ts` (ticket 035), because guard scope must match risk scope, not code-path convenience.

### The head-of-queue rule (why a cap must not throw forever)

The sweep takes unprocessed readings in the same order on every run. Any failure mode that both (a) blocks a reading and (b) leaves it unprocessed will therefore re-block the same reading on every docket pass and drain the run quota on it — the wiki stops accreting with no bad write to point at. Two rules close that:

- **Over budget → skip and record.** If `fitPayload` cannot fit one reading's mandatory core, T12 logs `mint-oversized` and appends a sweep-log line with `op: 'OVERSIZED'`. That line marks the reading swept, so it leaves the head. It is a distinct ledger op, so `store.oversizedReadingIds()` names exactly the set to re-sweep after the budget or the truncation rule changes. Skipping is recorded, reversible and countable — the thing Q-29 forbids is a silent bad write, not a logged deferral.
- **Repeatedly rejected → to the back.** Every rejected or failed attempt appends a sweep-log line with its reason. A reading whose attempts reach `sweep.attemptsBeforeBackoff` (3) sorts to the back of the sweep order and its count rides in `WikiReport.stuck`. It stays unprocessed, exactly as Q-29 requires; it just stops standing at the door.

### The UI decision — deferred, and why

**This slice ships:** a read-only wiki API (`GET /api/wiki`), a plain rendering of the claim essay in the existing style language, and the read-log write path (Q-21).

**This slice does NOT ship:** the six editing verbs (Q-33), Propagation (Q-4), the two-inks essay typography, or the time scrollbar (`docs/interface-references.md` § the document rule).

Three reasons, in order of weight:

1. **Propagation crosses into a different invariant region.** Q-33's Edit-body verb must mint a Snippet from the user's edit — that is the harvester/Vault snippet path, governed by Sole Authorship (Q-1), owned by files three other agents are editing right now. Bolting it onto this slice would put the Clerk's write boundary and the Snippet write boundary in one change.
2. **There is nothing to typeset.** Zero claims exist today. The document rule was written *because* the first wireframe pass "failed by accretion" — designing an essay renderer against imagined claims repeats exactly that failure. The reading surface should be designed against a real claim graph, which this slice produces.
3. **The verbs are cheap once the mechanics are right and expensive if they are wrong.** Each verb has a mechanical consequence (status recompute, archive-with-reason, cite detach → status recomputes). Those consequences are built and tested here as functions; wiring them to margin words is a small, design-led task afterward.

The minimum read surface stays *in* this slice because otherwise the slice is unverifiable by use — precisely the "unevaluable" gap the eval names in metrics 16–19. File a ticket for the editing slice (see Artifact Manifest).

## Storage layout (Q-3: markdown is truth, indexes derived)

```
vault/wiki/
  readings/<ulid>.md          EXISTS — gains `model:` + `modelAt:` + `at:` (Q-34, and B2's clock)
  claims/<ulid>.md            NEW
  contradictions/<ulid>.md    NEW
  candidates/<ulid>.md        NEW — ClashCandidates, Clerk-internal, never rendered (Q-30)
  registry/<slug>.md          NEW — identity/alias entries (Q-32)
  sweep-log.jsonl             NEW — append-only ledger: which reading got which op
```

**When a reading happened — one rule, one function.** `Reading` gains `at?: string`, written by `saveReading` from now on. Files written before this slice have no `at`, and there is no migration. The single defined value is:

```
readingTime(r) = r.at ?? new Date(decodeTime(r.id)).toISOString()
```

declared in `src/wiki/contract.ts` (T2) and called by every consumer. ULID `decodeTime` is not a second mechanism competing with `at` — it is the *defined value of `at`* for legacy files, applied in exactly one place. Verification: `decodeTime` appears in `src/wiki/contract.ts` and nowhere else in `src/wiki/` or `src/clerk/`. This is what makes "readings harvested since the question was asked" computable (Q-30 stage 3), and it is why the ClashCandidate file records `remeasureAskedAt`.

**Claim** — `vault/wiki/claims/<ulid>.md`:

```yaml
---
id: 01K…
range: "when he is talking about work he was hired for"   # MANDATORY, non-empty (Q-21)
status: unconfirmed                 # NEVER model-written; recomputed (Q-29)
cites: ["01K…@1", "01K…@2"]         # MANDATORY, ≥1, each must resolve on disk
facet: value
referents: ["my-manager"]           # registry slugs; the referent clash channel reads these
fromReadings: ["01K…"]              # lineage: which readings produced/updated this claim
attested: false                     # set only by a user verb (Q-33) — model has no path
readLog: [{ at: "…", surface: "wiki" }]   # Q-21 looping-effect flag
model: bonsai-27b                   # Q-34 stamp
modelAt: "2026-08-02T…"
created: "…"
updated: "…"
supersededBy: 01K…                  # present only on superseded claims
supersedeReason: "model-upgrade"    # REQUIRED whenever supersededBy is present (Q-29)
archived: true                      # ARCHIVE keeps the file — evidence, never deletion
archiveReason: "merged-into:01K…"   # REQUIRED whenever archived is true (Q-29)
---
One sentence of agent prose.
```

Body is agent prose — Q-1 bars the agent from Snippet and Piece text, not from Claim text; a Claim *is* agent prose by definition (CONTEXT.md — Claim). Wiki text never enters a Piece; that boundary is the composition slice's to hold.

**No confidence numbers anywhere. Coreness is computed from the citation graph on demand and never written to a file** (Q-21). Its one caller in this slice is T14, which orders claims within a facet by it; an export with no caller drifts.

**`fromReadings` is a typed lineage edge and never a substitute for `cites`** (CONTEXT — Two Planes). It exists so Q-34's lazy re-annotation can find which readings produced a claim. Evidentiary weight comes from `cites` alone, and a claim with `fromReadings` but no `cites` is rejected at the boundary like any other malformed claim.

**Contradiction** — `contradictions/<ulid>.md`: `{id, type: synchronic|diachronic, claims: [a, b], candidate: <candidateId>, remeasureQueueId, evidence: { snippetRef, quote, side }, status: open|dissolved, dissolveReason?, model, modelAt, opened, updated}`; body = the two quoted poles, dated (Juxtaposition material). `evidence` is the verified fragment that opened it — a Contradiction that cannot name the user's words that confirmed it does not open (Q-44).

**ClashCandidate** — `candidates/<ulid>.md`: `{id, pair: [claimA, claimB], channel: lexical|referent|embedding, status: pending-remeasure|confirmed|dissolved, outcome?, remeasureQueueId?, remeasureAskedAt?, model, modelAt, created}`. Dedupe key is the sorted claim-id pair — a dissolved candidate is never re-proposed (Q-30 stage 4, anti-repetition). `remeasureAskedAt` is set when the queue entry is minted and is the window's left edge for stage 3.

The type is `ClashCandidate`, not `Candidate`: CONTEXT.md already spends "candidate" twice (Arrangement candidates, and agent-minted Queue candidates) and lists it under *Avoid* for Buds. No glossary edit is needed for the longer name, which is the point of choosing it.

**Referent** — `registry/<slug>.md`: `{slug, canonical, kind: person|project|place|pole|construct|other, aliases: [...], model, modelAt, created, updated}`; body = optional agent note.

**`sweep-log.jsonl`** — append-only `{readingId, op, claimId?, reason?, at, model}`, where `op` is one of the six ClerkOps or one of two ledger-only ops: `OVERSIZED` (the payload would not fit; the reading is skipped and countable) and `REJECTED` (an attempt failed; the reading stays unprocessed and this line is what counts the attempt). Needed because a KEEP leaves no claim behind, so "already judged redundant" is otherwise indistinguishable from "never swept" (the whole point of Q-29's KEEP), and because without an attempt count a reading the model cannot handle eats the run quota forever. It is ledger, not truth: deleting it costs a re-sweep, never data — same posture as Cover's summaries. It is lineage, never knowledge (CONTEXT — Two Planes): nothing reads it into a Claim.

## Open Questions

These are unresolved from the documents, recorded rather than guessed.

### Cross-cutting
- **Does the head-of-queue rule bend Q-29?** Q-29 says a rejected op's reading "stays unprocessed for the next run". Two rules in this revision touch that: an oversized reading is marked swept (with a distinct `OVERSIZED` ledger op) rather than staying unprocessed, and a reading with 3+ failed attempts sorts to the back. The second is plainly compatible — the reading stays unprocessed, it just stops blocking. The first is a genuine narrowing: that reading is not retried until someone re-sweeps `oversizedReadingIds()`. **The judgment made here, stated so it can be overruled:** Q-29's rule protects against silent bad writes, and an over-budget reading produces no write at all, so skipping it with a countable, reversible ledger entry serves Q-29's purpose better than a deadlock that stops the wiki accreting with nothing to point at. If the register means "unprocessed, without exception", this plan is wrong and the correct fix is a smaller floor in `fitPayload`, not a skip — decide before T6 lands, because it is one branch.
- **Reading quality is upstream of everything.** Eval finding #7: facet labels are unreliable (`intention` applied to 5 of ~14 cuts, none correctly) and `superseded` never fires where it should. Claims mint from readings, and T9 now takes `facet` straight from the reading. This slice will faithfully turn bad readings into bad claims. Tickets 034/037 are in flight on that; **the RESULTS run should be done after they land**, or its claim-quality numbers measure the harvester, not the Clerk.
- **`expire()` never touches a drawn entry.** `src/queue/queue.ts:206` skips any entry whose status is not `pending`, so an entry that was drawn and never answered stays `asked` for good — it is not the 30-day expiry the review assumed. T17 makes `answered` reachable but does not change expiry, because widening `expire()` would change behaviour every existing queue test depends on, and that is outside this slice's scope. That is the conservative direction (never nag), but it is a leak, and it wants a ticket.

### BLOCKER

**B1. Q-30 stages 3–5 wait on a queue state the running app never produces.**
L581 keys confirmation on "each pending candidate whose re-measure queue entry
is now `answered`". `QueueStore.markAnswered` is defined
(`src/types.ts:160`, `src/queue/queue.ts:185`) and called by **nothing** —
`grep -rn "markAnswered" src/` returns the definition and the interface line,
no call site. `queue.draw()` sets `asked` (`queue.ts:173`) and the entry stays
`asked` until `expire()` kills it at 30 days. So stages 3, 4 and 5 of Q-30 are
unreachable in production, and T15's e2e (L654) will pass only because the test
sets the state by hand — eval finding #2 and learning #3 exactly: the test and
the implementation share an oracle the real system does not satisfy.
*Fix:* add a task that owns `src/elicitor/elicitor.ts` and `src/queue/queue.ts`
and marks the drawn entry `answered` when the user answers the turn it opened,
recording `answeredAt`. Both files are currently owned by no task in the
ownership table (L167–186). T15 must then drive the flow through the real turn
path, not through `queue.markAnswered` directly.

**B2. "the readings harvested since it was asked" (L581) is not computable.**
`Reading` is `{id, facet, stance, cites, reading}` (`src/types.ts:98`), and
`saveReading` persists exactly `{id, facet, stance, cites}`
(`src/vault/vault.ts:99-104`). A reading carries no timestamp, no session, and
no back-link to the sitting that produced it. `QueueEntry` carries no
`answeredAt` either. T12 job 5 therefore has no input.
*Fix, cheapest first:* T1 already opens `vault.ts` for the stamp — have
`saveReading` write `at` (or rely on `modelAt`) and have `rebuildIndex` read it
back, then window on `reading.at > candidate.remeasureAskedAt`. The ULID
prefix (`decodeTime`) is a second option and needs no schema change; pick one
and name it in T12's contract. Record `remeasureAskedAt` on the Candidate file
(L129) when the entry is minted.

**B3. T6 rebuilds the multi-item payload that ticket 034 just removed.**
L376 sends 6 readings, their cited snippets and 5 related claims in one call to
bonsai-27b. `src/harvester/harvester.ts:180-183` now sends **one user turn per
call** and `tests/harvest-chunked.test.ts` asserts it ("sends one call per user
turn, each carrying exactly that turn"). That change is the fix for eval
finding #1 — the failure the plan cites at L30 as its reason for caution. The
plan reasons from the finding and then adopts the shape the finding condemns.
Generating a validated op list is, as L30 says, harder than harvest JSON.
*Fix:* one reading per call. Payload = that reading + its cited snippets + ≤3
related claims. Accumulate ops across calls; per-call try/catch; per-call parse
mode, mirroring `HarvestDiagnostics` (`harvester.ts:152-172`), so a failed call
and an empty one never log alike. The "batch of 6" becomes a per-run call
quota. T6's open question (L702) plans to arrive here after T16 measures it;
the measurement already exists.

**B4. `capPrompt` throwing deadlocks the head of the sweep queue.**
`capPrompt` throws rather than truncating (L240), the throw happens before any
model call (L390), and a batch that fails leaves its readings unprocessed for
the next run (L35). The sweep takes unprocessed readings in the same order
every run (L577). An over-budget batch therefore throws forever, and because it
is always first, the 5-batch quota drains on it every docket pass — the wiki
stops accreting with no bad write to point at. The arithmetic is not
theoretical: 6 readings × 300 + 6 cited snippets × 400 + 5 claims × 200 = 5200
chars before the system prompt, against a 6000 budget.
*Fix:* on overflow, split the batch and retry down to a single item; if one
reading alone is over budget, log `mint-oversized` and write a sweep-log line
for it so it cannot block the head. B3's fix removes most of this, but the
single-item floor is still needed.

**B5. `judgeConfirmation` gates the Contradiction on an unverified model
boolean.** L407–409 returns `{confirmed: boolean, type, reason}`, with one
mechanical override (a `superseded` stance forces `diachronic`). Q-30 stage 3
makes this the single gate that opens a Contradiction, and eval finding #6
measured this exact shape degrading to `true` under mild pressure — the
`standalone` boolean took two obviously non-standalone fragments. The plan
applies the right medicine one function earlier (L404, poles verbatim) and then
skips it here.
*Fix:* require the confirmation to return a verbatim fragment of the
re-measure's cited snippet that carries the re-measured pole, and verify it as
a substring in code, exactly as L404 does. No verifiable quote → not confirmed
→ candidate dissolves. `confirmed: false` is already declared the expected
common case (L409), so this costs nothing when the model is honest.

**B6. `composeRemeasure` bypasses the validators ticket 035 landed.**
`src/elicitor/guards.ts` exports `isInterrogative` and
`hasFirstPersonOutsideQuote`, and every existing compose path runs both
(`src/clerk/composed.ts:109-110`). They exist because of eval findings #3 (a
flat declarative queued as an opener) and #5 (six person-agreement breaks in
one run), and learning #4 says guard scope must match risk scope, not code-path
convenience. L405 and its tests (L420) check the verbatim fragment, the
not-a-repeat rule, and that neither claim body appears — never that the output
is a question, never that person agrees.
*Fix:* T7 imports both guards from `src/elicitor/guards.ts` (public exports, no
new file ownership) and applies them with the same check-retry-null discipline
